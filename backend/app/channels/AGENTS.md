### IM Channels System (`app/channels/`)

Bridges external messaging platforms (Feishu, Slack, Telegram, Discord, DingTalk, WeChat, WeCom, GitHub, Buzz) to the DeerFlow agent via Gateway's LangGraph-compatible API.

**Architecture**: Channels communicate with Gateway through the `langgraph-sdk` HTTP client (same as the frontend), ensuring threads are created and managed server-side. The internal SDK client injects process-local internal auth plus a matching CSRF cookie/header pair so Gateway accepts state-changing thread/run requests from channel workers without relying on browser session cookies.

**References**: [IM_CHANNEL_CONNECTIONS.md](../../docs/IM_CHANNEL_CONNECTIONS.md) owns user-owned connections (bind flows, transfer semantics, file pipeline) plus the engineering contracts for stream publication, WeChat/WeCom media gating, Buzz subscriptions/trust, and channel-user-id context. [GITHUB_AGENTS.md](../../docs/GITHUB_AGENTS.md) owns the webhook-driven GitHub channel. Read the matching section before changing that area.

**Components**:
- `message_bus.py` - Async pub/sub hub (`InboundMessage` → queue → dispatcher; `OutboundMessage` → callbacks → channels)
- `store.py` - JSON-file persistence mapping `channel_name:chat_id[:topic_id]` → `thread_id` (`channel:chat` for root conversations, `channel:chat:topic` for threaded ones). Every access to `_data` must be protected by `_lock`; `list_entries()` snapshots keys and copies entries under the lock and formats only after releasing it.
- `manager.py` - Core dispatcher. Run dispatch per channel policy: `client.threads.create()` for threads; Slack/Discord on `client.runs.wait()`; Feishu/Telegram on `client.runs.stream(["messages-tuple", "values"])` for incremental outbound updates; same-thread Feishu turns serialize in-manager when `ChannelRunPolicy.serialize_thread_runs=True` so rapid follow-ups queue instead of tripping the runtime busy reply; `ChannelRunPolicy.fire_and_forget=True` channels switch to `client.runs.create()` (fire-and-forget, returns once the run is `pending`) so long autonomous runs do not hit the SDK default 300s `httpx.ReadTimeout`. Commands: `/goal` setting persists it through Gateway and then routes the objective as a chat turn; `/agent list` is owner-scoped and `/agent use` creates a fresh thread and persists the Custom Agent selection under both the channel restart key and Web's canonical routing metadata, so existing checkpoint lineage never changes agent across IM/Web.
  Stream publication is an **allowlist, not a denylist** (`_accumulate_stream_text`): only assistant message types (`ai`, `AIMessageChunk`, OpenAI-style `assistant`) — matched by prefix, never substring — become displayable text, and a bare `str` payload is never accepted. A swallowed streaming failure publishes its final outbound before releasing the inbound dedupe key, so a provider redelivery can retry without overtaking the terminal reply. Before changing stream publication or payload typing, read the [streaming publish contract](../../docs/IM_CHANNEL_CONNECTIONS.md#streaming-publish-allowlist); it records the hidden-context leak the allowlist closed and the payload shapes `_stream_payload_type` must handle.
- `base.py` - Abstract `Channel` base class (start/stop/send lifecycle). Provider callbacks that submit coroutines from SDK threads must use `_submit_threadsafe_coroutine()` (retains the real `asyncio.Task` on the owner loop; never treat `run_coroutine_threadsafe()`'s proxy Future as a completion signal); submission closes atomically with shutdown, and `stop()` must call `_close_and_drain_threadsafe_futures()` before tearing down SDK resources.
- `service.py` - Manages lifecycle of all configured channels from `config.yaml`. Shutdown closes manager admission first and keeps transports alive until every manager worker/follow-up watcher has exited. If the Gateway's outer timeout cancels shutdown, the service retains its channel objects and global singleton so unfinished resources are not detached and cleanup can be retried.
- `slack.py` / `feishu.py` / `telegram.py` / `discord.py` / `dingtalk.py` / `wechat.py` / `wecom.py` - Platform implementations. `feishu.py` tracks the running card `message_id` in memory and patches the same card in place. `telegram.py` accepts inbound text/photos/documents, preserves media captions, hands token-free attachment bytes to the shared upload pipeline, and sends final Markdown as Rich Messages through `channels.telegram.rich_messages` only when it is on **and** the text contains a rich construct (fenced code, emphasis, table, task list, `<details>`, block math, link) — structured command/error replies stay plain text so their newlines and `<placeholder>` tokens survive. `discord.py` registers typing loops before inbound handling yields and `_start_typing()` refuses work once `_running` is false; `stop()` runs on the main loop while typing tasks belong to `_discord_loop`, so cross-thread cleanup is scheduled there with a bounded wait and `_run_client()` drains tasks in its `finally` block; every outbound cross-loop call (`send` / `send_file` / `_get_channel_or_thread`) goes through `_run_on_discord_loop` with bounded awaits (30s send, 120s upload) that fail fast with a `RuntimeError` when the client loop is missing or not running — a dead client becomes a logged send failure instead of a permanently hung worker — and `is_running` reports client-thread aliveness so `ensure_channel_ready` can restart the channel after a fatal `_run_client()` exit. `dingtalk.py` optionally uses AI Card streaming when `card_template_id` is configured and overrides `receive_file` to download inbound images (`picture`/`richText`) and documents (`file`) by `downloadCode` into the thread uploads bucket, mirroring `feishu.py`.
- `wechat.py` / `wecom.py` - Inbound media URLs must pass a scheme + host-suffix allowlist before anything is fetched, size caps are enforced while streaming, no log line may contain any part of a media URL, and there is deliberately no URL re-fetch fallback — the manager reads only locally staged files. Before changing either connector's media handling, read the [inbound media gating contract](../../docs/IM_CHANNEL_CONNECTIONS.md#inbound-media-gating-wechatwecom).
- `buzz.py` - Buzz (Nostr relay) implementation: one NIP-42-authenticated websocket, pubkey-allowlist (deny-by-default) + mention/DM/thread-follow gating, streaming replies via in-place kind-40003 edits; requires the `buzz` dependency extra. The seen-event replay guard uses async `aseen()` / `arecord()` / `aflush()` boundaries off the Gateway event loop; `stop()` awaits the final flush and `start()` resumes scheduling and flushes dirty state. Subscriptions are strictly one REQ per channel (discovery without `#p`; live-scoped membership with `since`; one chat REQ per discovered channel); a relay `CLOSED` frame is recovered within per-subscription, per-auth-epoch budgets; `auth-required:` before the NIP-42 handshake is the expected bootstrap, not a refusal; replay cursors are per channel and never advance past `now + MAX_FUTURE_SKEW_SECONDS`; remote-fed state is capped (refuse, never evict); `send()` refuses text carrying hidden model-context wrappers (`_HIDDEN_CONTEXT_MARKERS`) because on Buzz a leak is a permanent public Nostr event. Before changing subscriptions, replay, trust, or shutdown handling, read the [Buzz connector engineering contract](../../docs/IM_CHANNEL_CONNECTIONS.md#buzz-connector-engineering-contract) (operator-facing subscription and trust models: [subscription](../../docs/IM_CHANNEL_CONNECTIONS.md#buzz-subscription-model), [trust](../../docs/IM_CHANNEL_CONNECTIONS.md#buzz-trust-model)).
- `github.py` - Webhook-driven GitHub channel. Inbound from `POST /api/webhooks/github`; outbound is log-only because GitHub agents post explicitly with `gh` from their sandbox. See [GITHUB_AGENTS.md](../../docs/GITHUB_AGENTS.md).
- `app/gateway/routers/channel_connections.py` - Browser-facing user connection and disconnect APIs
- `deerflow.persistence.channel_connections` - SQL-backed user-owned connection, optional credential, connect state, and conversation store

**Message Flow**:
1. External platform -> Channel impl -> `MessageBus.publish_inbound()`
   - For GitHub, the webhook router verifies the delivery then calls `fanout_event(bus, ...)`; matching agent bindings publish one `InboundMessage` each instead of a long-polling channel worker.
   - Telegram photo/document updates use the largest photo size or document metadata, preserve `message.caption`, enforce the hosted Bot API's 20,000,000-byte download ceiling, and never expose the token-bearing Bot API file URL. Downloaded bytes cross the adapter/manager boundary only through `message_bus.INBOUND_FILE_CONTENT_KEY`, which the manager consumes before persisting safe upload metadata.
   - Feishu/Lark inbound image/file downloads read at most 20,000,001 bytes and reject anything above 20,000,000 before persistence or sandbox sync. Oversize, unsafe-path, and path-resolution failures rewrite only that attachment placeholder to `Failed to obtain the [type]` so later attachments in the same message can still load.
   - WeChat/WeCom inbound media passes the [host-allowlist and streaming-cap gating](../../docs/IM_CHANNEL_CONNECTIONS.md#inbound-media-gating-wechatwecom) before fetch.
2. `ChannelManager._dispatch_loop()` consumes from queue
3. For user-owned channel connections, incoming messages carry `connection_id`, `owner_user_id`, and `workspace_id`; `owner_user_id` becomes the DeerFlow run `user_id`, while the raw platform user id remains `channel_user_id`. The Gateway accepts `channel_user_id` only from an internally authenticated channel caller's top-level `body.context`, clears it from both free-form `body.config` sections, and writes it into runtime context only (never `configurable`, which is checkpointed). It reaches sandbox commands as the fixed env var `DEERFLOW_CHANNEL_USER_ID` via a shell-quoted command-string prefix on every IM command (`export`/`unset`), never through `execute_command(env=...)`; the shell variable is informational, not authenticated identity. Non-IM runs are untouched. Tests: `tests/test_gateway_services.py`, `tests/test_channel_user_id_env.py`. Injection mechanism and session-semantics rationale: [channel user id runtime context](../../docs/IM_CHANNEL_CONNECTIONS.md#channel-user-id-runtime-context).
4. For chat: look up/create thread through Gateway's LangGraph-compatible API
   - First-use creation is serialized by a waiter-aware keyed lock over `(channel_name, chat_id, topic_id)`. Holders and queued callers share one lock generation through failure and cancellation; idle entries are reclaimed only after the final participant leaves. This prevents a late inbound message from bypassing a queued creator and splitting one conversation across duplicate Gateway threads.
5. Feishu/Telegram chat: `runs.stream()` → accumulate AI text → publish multiple outbound updates (`is_final=False`) → publish final outbound (`is_final=True`)
6. Slack/Discord chat: `runs.wait()` → extract final response → publish outbound
6b. GitHub chat (`ChannelRunPolicy.fire_and_forget=True`): `runs.create()` returns once the run is `pending`; the manager does not wait for the final state and does not publish an outbound. `ConflictError` on a busy thread still trips the standard `THREAD_BUSY_MESSAGE` path (log-only on GitHub); when the channel's policy also sets `buffer_followups_on_busy=True` (GitHub's default), the triggering message is buffered for a post-run follow-up instead of being silently dropped ([mechanics](../../docs/GITHUB_AGENTS.md#follow-up-buffering-while-busy-4121)).
7. Feishu channel sends one running reply card up front, then patches the same card for each outbound update (card JSON sets `config.update_multi=true` for Feishu's patch API requirement). Messages already sent inside an existing Feishu topic carry a compact source-message preview in that card, and queued same-thread follow-ups patch their own source message's card from queued → running → final without falling back to the generic busy reply.
8. Telegram streaming: the "Working on it..." placeholder message is registered as the stream target; non-final updates `editMessageText` it in place (channel-side throttle: 1s in private chats, 3s in groups due to Telegram's 20 msg/min group cap; 4096-char truncation; rate-limited updates dropped); the final update performs the last edit and splits >4096 texts into follow-up messages
9. DingTalk AI Card mode (when `card_template_id` configured): `runs.stream()` → create card with initial text → stream updates via `PUT /v1.0/card/streaming` → finalize on `is_final=True`. Falls back to `sampleMarkdown` if card creation or streaming fails
10. For commands (`/new`, `/status`, `/models`, `/memory`, `/goal`, `/agent`, `/help`): handle locally or query Gateway API. A Custom Agent also writes canonical `metadata.agent_name`, which makes thread-search results route Web continuation through `/workspace/agents/<name>/chats/<thread_id>`; `lead_agent` deliberately omits that canonical key and stays on the ordinary chat route. The manager caches `channel_agent_name` for the hot path and reloads it after restart before routing a resumed turn. An explicit selection also normalizes `agent_name` across top-level run context plus the existing RunnableConfig `context` and `configurable` carriers (or clears all three for `lead_agent`) before Gateway's `setdefault` compatibility merge, so stale channel defaults cannot silently win.
11. Outbound → channel callbacks → platform reply
    - GitHub is the exception: the channel logs the final assistant message and does **not** auto-post it to GitHub. Agents use the sandbox `gh` CLI for intentional writeback, so silence is cheap when several agents fan out on the same event.

**Owner-scoped file storage**: inbound files, uploads, and output artifacts are staged under the DeerFlow owner's bucket (`users/{user_id}/threads/{thread_id}/user-data/{uploads,outputs}`). `ChannelManager._handle_chat` resolves the storage owner once via `_channel_storage_user_id(msg)` and threads it as the `user_id=` kwarg through the whole pipeline (`receive_file`, `_ingest_inbound_files`, `_resolve_attachments`/`_prepare_artifact_delivery`); the cached value is reused for both the blocking (`runs.wait`) and streaming paths, so uploads and artifact delivery always target the same bucket. The bucket id matches the memory bucket resolved by `_resolve_memory_user_id` (both normalize through `make_safe_user_id`). Artifact delivery resolves only from the bound owner's outputs through `app.gateway.path_utils.resolve_outputs_confined_path`, the same outputs-only rule the artifact editor uses, so a sibling `uploads/`/`workspace/` path or a symlink planted in `outputs/` is skipped with a warning. Pipeline detail: [Owner-scoped File Storage](../../docs/IM_CHANNEL_CONNECTIONS.md#owner-scoped-file-storage).

**Configuration** (`config.yaml` -> `channels`):
- `langgraph_url` - LangGraph-compatible Gateway API base URL (default: `http://localhost:8001/api`)
- `gateway_url` - Gateway API URL for auxiliary commands (default: `http://localhost:8001`)
- In Docker Compose, IM channels run inside the `gateway` container, so `localhost` points back to that container. Use `http://gateway:8001/api` for `langgraph_url` and `http://gateway:8001` for `gateway_url`, or set `DEER_FLOW_CHANNELS_LANGGRAPH_URL` / `DEER_FLOW_CHANNELS_GATEWAY_URL`.
- Per-channel configs: `feishu` (app_id, app_secret), `slack` (bot_token, app_token), `telegram` (bot_token, optional `rich_messages`), `dingtalk` (client_id, client_secret, optional `card_template_id` for AI Card streaming), `github` (operator kill-switch `enabled`, plus `default_mention_login` for mention-required triggers), `buzz` (relay_url, private_key)

**User-owned channel connections** (`config.yaml` -> `channel_connections`):
- Disabled by default; a user-binding layer on top of the existing `channels.*` runtime config, not a replacement for provider bot credentials. No public IP, OAuth callback URL, or provider webhook route is required.
- Telegram uses a deep-link `/start <code>` flow over the existing long-polling worker; Slack, Discord, Feishu/Lark, DingTalk, WeChat, and WeCom use `/connect <code>` over their existing outbound channel workers.
- Bind-order and transfer invariants are contract: a valid connect code is consumed **before** the `allowed_users` filter (bind security rests on the code's confidentiality — `secrets.token_urlsafe(16)`, 600s TTL, one-time — not on the allowlist), and the latest successful bind wins per `(provider, external_account_id, workspace_id)`, enforced by the partial unique index `uq_channel_connection_active_identity`. Full model: [Connect Flow](../../docs/IM_CHANNEL_CONNECTIONS.md#connect-flow) and [Security Notes](../../docs/IM_CHANNEL_CONNECTIONS.md#security-notes).
- WeChat polling timing settings accept only positive finite seconds (invalid values fall back to defaults); WeCom serializes `start()`/`stop()` per instance and caps outbound at the protocol's 20480 UTF-8 bytes (stream clip on a character boundary; pushes split into at most 10 sequential markdown messages; per-chat send lock serializes each batch). Detail: [WeChat and WeCom connection runtime limits](../../docs/IM_CHANNEL_CONNECTIONS.md#wechat-and-wecom-connection-runtime-limits).
- Provider-level `connection_status` reflects the user's newest connection row: `not_connected` with no binding, except in auth-disabled local mode where a configured running channel reports `connected`. Slack replies use the configured operator bot token unless per-connection credentials are present; unreadable or corrupt stored credentials are treated as unavailable.
- Telegram, Slack, Discord, Feishu/Lark, DingTalk, WeChat, and WeCom workers resolve incoming platform identities to connection records before reaching `ChannelManager`.
- Browser APIs (`GET /api/channels/providers`, `GET /api/channels/connections`, `POST /api/channels/{provider}/connect`, `DELETE /api/channels/connections/{connection_id}`) remain protected by normal Gateway auth/CSRF; provider messages arrive through the already-configured channel workers.

**GitHub event-driven agents** (webhook-driven IM channel):
- Custom agents declare a `github:` block in their `config.yaml` to bind to repos and event triggers; the webhook route is fail-closed (mounted only when `GITHUB_WEBHOOK_SECRET` is set, or dev opt-in `DEER_FLOW_ALLOW_UNVERIFIED_GITHUB_WEBHOOKS=1`) and exempt from auth/CSRF because authenticity is enforced by HMAC.
- Registry caching is keyed by the configured agent store's opaque signature: file storage uses agent config mtimes, while database storage hashes the ordered owner/name/config/soul contents so same-timestamp writes still invalidate webhook routing.
- Outbound is **log-only** by design; `fire_and_forget=True` plus `buffer_followups_on_busy=True` (GitHub's default) buffers follow-ups while busy. Architecture, dispatch, thread determinism, mention precedence, token lifecycle, race recovery, buffer mechanics, and the per-process scope limitation: [GITHUB_AGENTS.md](../../docs/GITHUB_AGENTS.md).
