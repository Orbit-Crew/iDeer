# Task-branch reviewer matrix

This matrix holds expected answers for independent review of branch navigation. It is not a coding-agent route and must stay outside reader prompts, reader candidates, task routes, and scored reading material. Agent-facing routes remain the current sources of entry points and validation steps.

| Test addition | Add a new test without moving or deleting an existing one. | Test directory ownership, coverage matrix, current lane selection/reuse rules, and inventory after addition. | Test migration | Move or rename a test file/node. | Preserve assertions and collected test identity; follow the migration method, record keeper/replacement and equivalent-or-stronger evidence, update inventory and migration ledger. | Historical migration batches only when a similar batch informs the current move. | Focus the moved test by its new path, then `python3 scripts/test_inventory.py`; compare collected node IDs. | If node identity changes intentionally, explain the ownership and ledger impact rather than treating the move as path-only. |
| Test deletion | Remove a test or collected node. | Preserve required behavior coverage through an equal-or-stronger keeper/replacement, execution ownership, migration ledger evidence, and updated inventory. | Old migration batches only when they help determine replacement quality. | Run the keeper/replacement test, then `python3 scripts/test_inventory.py` and verify the removed node. | If no keeper exists, report a coverage gap instead of assuming deletion is safe. |
| Multiple behaviors | One task changes more than one branch above. | Union all triggered branch obligations, owners, conditions, and first focused validation hops. | Include only decisions activated by one or more branches. | Run the union of first focused checks named by each triggered branch. | Do not stop after the first branch if another behavior is named or implied by the concrete diff. |
| Ambiguous task boundary | The task does not identify the changed layer, operation, or lifecycle. | Record what is unknown. Perform narrow source verification or ask for clarification before deciding a branch is inapplicable. | Expand only the branch selected by that verification. | Resolve the branch through the source call path, then use that branch's first focused check. | An unknown trigger stays unresolved; it is not an implicit “no”. |

## Permissions source-scope key

Use chapter labels and heading anchors explicitly:

- `permission-model-redesign.md` chapter I, **权限模型与规则**, contains the current permission and approval semantics described by its implementation-state note. The route's anchors `#2-design-principles`, `#3-角色与权限`, and `#4-浏览权限visibility-控制` are subsections of this chapter.
- Chapters II–V are the 2026-07 database, API, frontend, and migration design baseline. The implementation-state note identifies API §§3.7 (visibility approval) and 3.8 (audit logs) as matching current routes; treat only those matching portions as current references when triggered. Chapter IV remains unverified page by page, and chapter V records executed historical migrations.
- `permission-matrix.md` role-by-operation and visibility semantics are current; its API, database, frontend, and migration sections are design baseline. Current route/service behavior remains the implementation authority.
- The current list contract also includes the root KnowledgeBase interface rule and Resource Governance V2 ownership for `/api/resources`. The legacy design documents do not replace that contract.

This key resolves the numbered-section ambiguity identified by the navigation specification. It does not rewrite either permission document, nor does it make every subsection current implementation detail.
